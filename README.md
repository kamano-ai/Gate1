# Gate1 提出物

社内問い合わせ管理システムの「ステータス変更・担当者割り当て機能」。配布資料の要件定義書 v1.2 を基準に実装しています。


## 1. 起動手順

Python 3.10以上。アプリ本体の外部依存パッケージはありません。DBはSQLiteです。

```powershell
cd C:\Users\A_K_O\vexum\研修\研修１
.\run.ps1
```

PowerShellのスクリプト実行が制限されている場合や、他のOSでは、Pythonで直接起動できます。

`run.ps1` はWindows PowerShell 5.1でも文字コードの誤認が起きないよう、ASCII文字のみで記述しています。初版の日本語エラーメッセージによる構文エラーは修正済みです。

```text
python app.py --port 8000 --user 1
```

このPCのCodex同梱Pythonで直接起動する場合：

```powershell
& "$env:USERPROFILE\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe" app.py --port 8000 --user 1
```

ブラウザで <http://127.0.0.1:8000/?id=1> を開きます。初回起動時に `data/gate1.sqlite3` を作成し、問い合わせ5件とユーザー4件を投入します。再起動しても変更内容は保存されます。終了は起動したターミナルで Ctrl+C。

### 既存システム部分の検証用前提

資料では登録・一覧表示が実装済みという想定ですが、提供されたフォルダに既存コードはありませんでした。そのため、詳細画面に移動するための読み取り専用一覧と初期データを用意しています。登録・削除・ユーザー管理は追加していません。

認証システムは提供されていないため、ログイン済みユーザーをサーバー起動時の `--user` で固定します。ブラウザからユーザーIDやroleを送っても操作者は変わりません。本番用ログイン認証の実装ではなく、既存認証を再現するローカル検証用の前提です。サーバーは127.0.0.1でのみ待ち受けます。

| ID | 氏名 | 権限 | 有効 |
|---|---|---|---|
| 1 | 佐藤 花子 | ADMIN | true |
| 2 | 鈴木 一郎 | MEMBER | true |
| 3 | 田中 美咲 | MEMBER | true |
| 4 | 山田 次郎 | MEMBER | false |

MEMBERの画面は、別のターミナルで同じDBを使用して起動します。

```powershell
.\run.ps1 -Port 8001 -UserId 2
```

<http://127.0.0.1:8001/?id=1> を開きます。有効でないユーザーIDでは起動できません。

検証で初期データからやり直す場合、使用中のDBを削除せず、未使用のDBファイル名を指定できます。

```powershell
.\run.ps1 -Port 8002 -Database data\capture.sqlite3
```

## 2. 動作確認手順

### 初期問い合わせ

| URLパラメータ | 初期状態 | 担当者 | 優先度 |
|---|---|---|---|
| ?id=1 | NEW | 未割り当て | 中 |
| ?id=2 | IN_PROGRESS | 鈴木 一郎 | 高 |
| ?id=3 | PENDING | 田中 美咲 | 低 |
| ?id=4 | DONE | 佐藤 花子 | 中 |
| ?id=5 | NEW | 鈴木 一郎 | 中 |

1. 管理者で `?id=1` を開く。変更先は「対応中」のみ、履歴は「変更履歴はありません」。
2. ステータスを変更する。現在が「対応中」になり、担当者が佐藤 花子に自動設定され、履歴が2件増える。
3. 「保留」へ変更し、変更先が「対応中」のみになることを確認する。「対応中」に戻してから「完了」へ変更する。
4. 完了時は担当者変更ボタンが非活性で、ステータス変更先は「対応中」のみ。「対応中」へ戻すと再オープンする。APIの `closed_at` がNULLになることも確認できる。
5. MEMBERで `?id=5` を開く。担当者変更ボタンが非活性で、管理者に依頼する案内が表示される。
6. 管理者でNEWの問い合わせを未割り当てに戻す。MEMBERで再読み込みし、自分に割り当てる。他人を選択して送信すると権限エラーになる。
7. ステータス変更コメントに201文字入力して送信する。指定の文字数エラーが出て、状態は変わらない。200文字は受け付ける。
8. 同じ問い合わせを2タブで開き、片方で変更後、もう片方で更新する。更新競合のメッセージが表示される。再読み込みして最新情報を取得する。
9. `?id=999` を開くと、問い合わせが存在しないメッセージが出る。

### 自動テスト

```powershell
.\test.ps1
```

または `python -m unittest discover -s tests -v`。毎回、一時DBを作成するため通常のデータを変更しません。全16組の状態遷移（許可5組、拒否11組）、権限、履歴、コメント境界、排他制御、ロールバックを検証します。ロールバック試験ではSQLiteトリガーで履歴INSERTを意図的に失敗させ、本体と履歴が試験前と完全一致することを確認します。自動割り当てでは2件目の履歴を失敗させ、1件目の履歴も取り消されることを確認しています。

ブラウザテストはNode.js、Playwright、Microsoft Edgeがある環境で実行できます。このPCではCodex同梱Playwrightを使用します。他の環境では `npm install --no-save playwright` が必要です。アプリ起動自体には不要です。

```text
node tests/browser.cjs
```

専用の一時DBとサーバーを自動起動し、終了時にサーバーを停止します。スクリーンショットは撮影しません。

## 6. 振り返り


### 6-1. 実装前に判断に迷った箇所

基本AIに課題内容の理解をさせてから実装に取り掛かったため、実装の上で、何か迷った箇所はない。しかし、AIにこの件を尋ねたところ、下記の出力が得られた。要件定義書を詳細に書いてもなお、どこかに不備があるかもしれないことを念頭に入れ、再確認を繰り返すべきであると感じた。

- コメント欄はあるが保存先のカラムがない。任意入力と200文字以内の検証のみ実装し、DB項目や履歴へのコメント表示は追加しなかった。
- NEWからの自動割り当ては担当者変更でもあるため、2.5とR-06に従い、ステータス履歴・担当者履歴を1件ずつ同一トランザクションで保存した。
- 担当者変更時のupdated_at更新はR-06には明記されていないが、N-02の競合検出を担当者変更にも成立させるため、担当者変更時にも更新した。
- 氏名の読み仮名の保存先がない。DB定義は維持し、検証用ユーザーに読み情報を付けた。
- R-05違反専用の文言はないため、「この操作を行う権限がありません。」を使用した。
- 同じ担当者への再送信の扱いは未記載。管理者による同値指定は成功応答とし、実際の変更がないため履歴・updated_atは増やさない。MEMBERの設定済み問い合わせへの操作は同値でも拒否する。
- 複数の違反が同時にある場合の優先順位は未記載。存在・操作者・競合を確認してから、担当者変更ではDONE制約、権限、割当先の妥当性の順に検証する。
- SQLiteの自動採番は `INTEGER PRIMARY KEY AUTOINCREMENT` を使用した。これは64ビット整数で、資料のBIGINT/AUTOに対応する。VARCHARの長さはSQLite自体では強制されないが、対象機能は件名・氏名等の登録更新を行わず、更新値は定義済みコード・有効IDに限定する。
- 仕様の9メッセージと競合メッセージに加え、通信障害・DB障害・不正なJSON等には技術的な失敗表示を設けた。仕様で文言が指定されているケースは指定文言を使う。

### 6-2. 最初のAIプロンプトで伝え忘れた部分

まず、配布資料全文の読解と全体像の理解をAIにさせたことで大きな伝達漏れはなかったと考える。ただ、どのように実装したのか、そのプロセスを出力させなかったため、セルフチェック時にうまく実現できているか確認するのに時間を費やしてしまった。この点は次回以降の研修から活かしていきたい反省である。

### 6-3. 要件定義書がなかった場合に確認したいこと
